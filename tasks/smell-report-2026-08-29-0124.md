## 执行摘要

项目是**健康的分层模块单体**：组件 → api 薄封装 → bindings → services → repository → database/sql，AGENTS.md 声明的架构不变量绝大多数被代码忠实执行。安全防线（参数绑定 + 标识符白名单 + DDL 后端集中生成）贯彻一致；无 TODO/FIXME、无 `any`、无 console.log、无裸 panic；并发处理认真（store 双重检查、countSeq/alive 竞态防护、Events.On 正确 Off）。整体质量明显高于同类规模项目。

但存在 **3 个真实缺陷级问题**（均为"行为与注释/预期不符"型，非架构性）：JSON 导出复用 UI 展示协议导致数据截断、导入列名去重算法破坏唯一性不变量、危险 SQL 检测的 WHERE 判定注释与实现相反。另有 10 个警告、14 条建议。

**Critical: 3 | Warning: 10 | Suggestion: 14**

## 发现清单

### 🔴 关键（真实缺陷）

**#1. JSON 导出复用 cell.Encode，大文本被截断且 UI 内部标记泄漏进导出文件**
- **反模式:** Leaky Abstraction + 行为不一致（三后端漂移）
- **位置:** `internal/exporter/exporter.go:291-297`（jsonValue），对照 `csvValue`(:278) 与 `xlsxValue`(:164)
- **证据:** jsonValue 的 default 分支为 `return cell.Encode(v)`。cell.Encode 是 UI 展示协议：>1MB 字符串返回 `{__kind:"text-truncated", value: 前缀}` 标记、超 ±2^53-1 整数返回 `{__kind:"bigint", str}` 标记。CSV/XLSX 分支注释明示"文本原样写入完整内容，不做 UI 截断"，JSON 却会静默截断大文本并把 `__kind` 内部协议写进用户导出文件。
- **建议:** jsonValue 与 csvValue/xlsxValue 对称：string 原样输出、int64/float 用 strconv 全精度格式化，不复用 cell.Encode。

**#2. DedupeColumns 生成的去重名与真实列名冲突**
- **反模式:** 算法不变量破坏
- **位置:** `internal/tabular/tabular.go:130-145`
- **证据:** `seen` 只登记原始名。输入 `["a", "a", "a_2"]` → 第二个 "a" 生成 "a_2" 但未写回 seen → 输出 `["a", "a_2", "a_2"]`，与真实 "a_2" 撞名。导入/建列的唯一性承诺失效。
- **建议:** 每个最终输出名都登记 seen（含生成名），循环直至唯一。

**#3. hasTopLevelWhere 对子查询/字符串内 WHERE 的判定与注释意图相反（危险检测漏判）**
- **反模式:** Lying Comment + 漏判
- **位置:** `internal/sqliteutil/sqlkind.go:281-284`
- **证据:** 实现为 `strings.Contains(strings.ToUpper(s), "WHERE")`，不剥离字符串字面量。`UPDATE t SET x = (SELECT ... WHERE ...)` 无顶层 WHERE 却命中 → 判定"有 WHERE" → 不再提示"将更新整表"。注释声称"子查询中的 WHERE 也算命中，宁可多提示"，实际行为是少提示。
- **影响:** 仅影响危险确认弹窗的提示完整性；执行本身仍受 ValidateSingle/SplitStatements 保护，非注入漏洞。
- **建议:** 剥离字符串字面量后再检查，或至少按注释意图改成更保守判定（如同时检查 UPDATE/DELETE 与顶层 WHERE 的语法位置）。

### 🟡 警告

**#4. God 函数：buildRedesign 约 500 行（redesign.go:109-610）**
预览/执行共用路径，承载校验 + 阻断判断 + 语句序列生成 + 执行计划，是全库最大单函数、回归风险最高点。建议按阶段拆分为 buildRedesignValidation / buildPlan / buildStatements。

**#5. 长方法 + 深嵌套：GetTableData 约 260 行（data_repository.go:82-345）**
游标模式组合（单列/复合/排序/NULL 回退/OFFSET）分支最深 5 层。防御与注释到位、正确性无虞，但为维护难点。建议拆分 buildCursorSelect / buildCursorInfo。

**#6. 错误分类缺失，驱动裸错误外泄**
- `repository/errors.go` 仅 ErrNotOpen 一个哨兵；`schema_repository.go:753-757` Exec 直接 return 裸驱动错误；全库大量 `fmt.Errorf("...: %w", err)` 把英文 SQLite 消息拼进中文串直出前端，前端只能解析文本。
- 建议: repository 边界建立 constraint/syntax/busy/no-rows 分类 + 统一 wrap，前端按类别处理。

**#7. 服务层越过 repository 直取 *sql.DB（违反 AGENTS.md 不变量 1 字面约定）**
- `services/export_service.go:58,81`、`services/import_service.go:79` 直接 `s.store.DB(connID)` 并把裸句柄交给 exporter/tabular 执行查询。
- 实用主义（流式导出需要查询句柄）但违反文档承诺，且查询执行散落层外。建议：Store 增加"导出/导入用查询执行器"方法（带 ctx、返回已编码行），把 DB 句柄留在 repository 内。

**#8. N+1 PRAGMA 扫描 + 静默吞错（schema_repository.go）**
- 补全 schema（:721,726 每表一次 table_info）、全库外键（:825,830 每表一次 foreign_key_list）、索引列（:230,235 / :326,327 每索引一次 index_info）三处 N+1；内层循环 Scan 错误被 `continue` 吞掉（列数据静默缺失），rows 非 defer 关闭（单连接下提前 return 会占死连接）。
- 典型桌面场景表数少，影响有限；建议至少抽公共扫描辅助 + 吞错改记日志。

**#9. 连接生命周期竞态（store.go）**
lookup 返回裸 *Conn 指针不持锁（:202-208），CloseConn 删 map 后释放锁再 cancel+Close（:146-163）——并发下调用方可能在 Close 后仍使用已关 db。baseCtx 取消不覆盖无超时的长查询（data_service 直接用 baseCtx）。桌面单窗口场景触发概率低，建议文档化"调用方生命周期短于 Store"不变量，数据路径统一派生超时 ctx。

**#10. BLOB 先全量读入再拒绝（data_repository.go:768-778）**
`Scan(&data)` 先把整列读进内存，之后才检查 `len(data) > 32MB`。超大 BLOB 白读全量。建议 `SELECT length(col)` 前置判断或 substr 截断探测。（注：base64 编码在大小检查之后才执行，无额外浪费。）

**#11. TableDataPage 主数据加载无过期响应防护（TableDataPage.tsx:113）**
countSeq 只保护行数统计，`setData(result)` 无序号/Abort 防护。快速翻页/改筛选时旧响应可能覆盖新数据。Wails IPC 基本串行、概率低，但修复成本极低：同款 seq guard 即可。

**#12. QueryPage 并发执行无防护（QueryPage.tsx:88-160, 203-216）**
tryRun 与 Ctrl+Enter 处理器均不检查 running，快速双击可并发执行、互相覆盖 result/batch。`if (running) return` 一行可修。

**#13. 重复代码族（5 处，均 ≥3 处重复）**
- PRAGMA table_xinfo 列扫描手写三份（schema_repository.go:133-141, 375-385, 407-417）+ GetSchema 四联块（:40-117）逐行同构
- 过滤/排序 WHERE 构造在 GetTableData 与 countRows 重复（data_repository.go:99-132 vs 152-185）
- 重建分块拷贝与传输分批几乎同构（schema_repository.go:575-641 vs transfer_repository.go:317-358）
- 前端连接过滤 `conns.find(c => c.id === connId)?.schema` 7 处（CreateTableModal:49、ImportWizard:26、RedesignModal:71、TransferWizard:27/110、QueryPage:41、TableDataPage:76、ViewDesignerModal:29）
- `__kind` 裸魔法字符串判别 3 处（DataGrid.tsx:258-260、TableDataPage.tsx:627-630、CellView.tsx:17-50），绕过 types 的类型守卫

**#14. 魔法字符串/吞错散落**
- "数据库以只读方式打开"错误文案约 10 处、"已存在同名对象"约 6 处
- cell.Decode 用 `t["__kind"]/["b64"]/["str"]` 字段名字面量与 Marker JSON tag 解耦（改 tag 静默破坏 Decode）；1e15 阈值 Encode/Decode 两处硬编码

## 我的独立判断要点（与其他审查者的差异点）

1. **N+1 PRAGMA 扫描定级为警告而非关键**：SQLite 桌面客户端场景表数量通常几十张、PRAGMA 单次微秒级，实际影响有限；真正的风险是伴随的吞错与 rows 关闭方式。
2. **store.go 竞态定级为警告而非关键**：触发需要 CloseConn 与查询并发，Wails 单窗口调用基本串行。
3. **三个"关键"全部落在 internal/ 包**，且全部是"实现与注释/预期相反"型，说明该层最需要测试补强（exporter/tabular/sqliteutil 缺针对性单测）。
4. **测试覆盖是最大短板**：前端零测试；后端测试集中在 repository/services，internal 的 exporter/tabular/sqliteutil 是安全关键路径却覆盖最薄——本次三个关键缺陷恰好都在这三个包，非偶然。
